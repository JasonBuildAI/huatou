# 宿主接法（integration）

这份文档是给宿主作者的：怎么把 huatou 接进一条真实的流水线。每一节回答一个
「不这么做会怎样」—— 判据本身的来源在 [`rules.md`](rules.md)，边界在 [`design.md`](design.md)。

## §1 一张图：五个调用点

```
用户消息进来 ──note_user_spoke────────────────────────────────────────┐
                                                                    │
页面打开 / 一个回合收尾 ──arm_after(state, channel) ──► 挂表 … 定时器到点
                                                                    │
                                      主动请求到达 ──may_open(state, channel)
                                                                    │
                                                   放行 → 出稿 → line_rejected(第一句)
                                                                    │
                                      真的发出去了 ──note_opened───┘
                                                     note_said / note_her_ask

用户消息进来（答她）── note_user_spoke ＋ 出稿前 should_hand_back(state, user_msg)
```

两条分工贯穿全库，接错任何一条都会把状态弄成两处真源：

- **判定只读**：`may_open` / `should_hand_back` / `arm_after` / `line_rejected` /
  `must_wait` / `asks_the_user` 一个字节都不写。它们可以随便调用、随便打日志、
  随便在面板上跑。
- **改写只有 `note_*`**：`note_user_spoke` / `note_opened` / `note_said` /
  `note_her_ask` 是仅有的入口。宿主调错一次（比如「放行但最终没发出去」也调了
  `note_opened`），症状是「她少说了一句」，而日志上什么都看不出来。


## §2 布防与还机会

「安静够了吗」有两个消费方，分开回答，**不许两处各判一遍**（`rules.md` §3.1）：

| 谁 | 什么时候问 | 回答什么 |
|---|---|---|
| 宿主（布防） | 页面打开、一个回合收尾、或「这一次暂时不合适」之后 | `arm_after(state, channel=…)` → 还要安静多少秒；`None` = 不挂表 |
| 服务端（放行） | 主动请求真的到达时 | `may_open(state, channel=…)` —— **再判一次**，坏掉的客户端不能把钱烧光 |

`arm_after` 返回 `0.0` 就是「现在就请求」；返回 `None` 有四种，对宿主是同一句话
「现在别挂表」，但原因分两类：

| 不布防的原因 | 类别 | 什么时候会重新布防 |
|---|---|---|
| 功能关掉了（`max_streak = 0`） | 终局 | 宿主改配置 |
| 连试上限到了（`streak >= max_streak`） | 终局 | 用户真实开口（`note_user_spoke`） |
| 她问过，还没等到回话 | 暂时 | 用户真实开口 |
| 文字端这一回合已经主动挑过一次 | 暂时 | 用户真实开口 |

「暂时」那一列的两次重新布防只来自一个事件：用户真的说了话。宿主收到用户消息时，
先 `note_user_spoke`，再在那一轮的收尾重新 `arm_after`。

### 还机会：定时器到点、但时机不合适

定时器响了、`may_open` 也放行，但**说话的时机**不合适的场景有两种处置方式。
源系统在这一格上踩过坑，原话是：不还的话这一次就永久没了，此后她再也不会
主动开口，直到用户再发一条消息 —— 「她会先开口」这条能力会**静默**失效。

| 触发时发现 | 还机会吗 | 为什么 |
|---|---|---|
| 用户正在看查找定位到的旧记录 | **还**（重挂一次表） | 那是暂时不合适；这一次让出去，下一次该触发还得触发 |
| 输入框里有没发出去的字 | **还** | 同上 |
| 正忙着出一轮稿 | 不还 | 那一轮的收尾本来就会重新布防，再挂一次只是抢同一次表 |
| 正在收音（通话里） | 不还 | 收音的收尾会重新布防，同上 |
| 连试上限到了 | 不还 | 终局语义：服务端的 `may_open` 也会再挡一次 |
| 她问过，还没等到回话 | 不还 | 那是等用户真实开口的状态，不是「时机不对」 |

「还机会」在 huatou 里就是再调一次 `arm_after` 并重挂表 —— 它没有单独的接口，
因为这一档不需要新的状态：`arm_after` 读的还是同一份 `State`。

## §3 刷新继承：状态要跟着会话走

用户刷新页面之后，**已经用掉的机会**与「问后等待」都必须从落盘的状态里读回来 ——
否则刷一下就能骗她再问一次，而那是一条能被用户利用的漏洞（`design.md` §3.1）。

两个方向各一个函数，形状是普通 JSON：

```python
payload = state.to_dict()            # 下发 / 落盘：只放 JSON 装得下的东西
state = State.from_dict(payload)     # 读回：认不出的键忽略，坏值取默认
```

```json
{
  "streak": 1,
  "last_open_ts": 1780000000.0,
  "text_fired": true,
  "waiting_user": true,
  "her_ask_streak": 1,
  "recent_said": ["今天画了五版，手都酸了。"],
  "last_activity_ts": 1780000000.0
}
```

三件容易漏掉的事：

- **`recent_said` 也要持久化。** 它是逐字重复那条判据的比对方；只存计数不存
  说过的那几句，刷新之后同一句话就能再出口一次 —— 而「同一句出现两次」正是
  那条判据存在的理由。
- **失败姿态是放宽，不是锁死。** 认不出的键忽略、坏值取默认、老键名
  （`proactive_*` 那一套、布尔量 `last_her_ask`）认得出就迁移；绝不因为一份状态
  读不懂就永久关掉某项能力（`rules.md` §6.4）。
- **`to_dict` 交出去的是副本。** 宿主那边一次 `append` 不该改到活状态；
  判定与持久化之间的边界靠这一条守住。

## §4 四个 `note_*` 各落在哪

| 宿主里的时刻 | 调什么 | 备注 |
|---|---|---|
| 收到一条**非空**的用户消息 | `note_user_spoke(state)` | 空消息（误触、VAD 碎片）不算开口 |
| 她主动开口的那一轮**真的发出去了** | `note_opened(state, channel=…)` | `channel` 必须说清：`text_fired` 只对文字端生效 |
| 她的出稿真的说出口了（主动与普通回复**都要**） | `note_said(state, 完整消息)` | 逐字重复比的是这里记下来的话 |
| 每一轮出稿之后 | `note_her_ask(state, floor.asks_the_user(...))` | 见下面那条最常被漏掉的覆盖 |

`asks_the_user` 的输入是**这一轮出稿的每一条消息**：源系统的口径是
`any(asks_the_user(m) for m in replies)` —— 只要有一条在问他，就算她在等他回话。

### 「放行且真的发出」由宿主定义

`note_opened` 的触发点有一个必须写死的选择：是「放行的那一刻」还是「请求真的
出去了的那一刻」。源系统选前者，理由是那次尝试即使被客户端掐断也要跨刷新留住；
本库把它交给宿主，因为只有宿主知道「发出去」发生在哪一层。**选一种，写进自家
文档，别两头都调** —— 两头都调的话 streak 会一次记成两回。

### 最常被漏掉的一条：`note_her_ask` 必须覆盖普通回复路径

回他的那句话里带反问，也要记。只在主动开口那一轮写状态，就会漏掉最常见的
文字回复路径：用户没回答她的反问时，再定时追问会像催促 —— 而那正是
`waiting_user` 要挡的形状（`design.md` §5 里对 `note_her_ask` 的原话）。

```
他问 → 她答（答里有反问）→ note_her_ask(True) → waiting_user = True
                                 ↓
                        定时器到点：may_open 返回 waiting_user
                                 ↓
                        他开口 → note_user_spoke → 解除
```
