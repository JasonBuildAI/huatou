## 0. 一句话

**一个只回答「这一句该不该由她说出口」的发言权管理器。**

它不生成内容、不合成、不播放、不检索；它把「什么时候可以开口、答完要不要把话头递回去、
递了之后等不等、这句话能不能出口」从产品代码里的 if 堆，变成一个可注入时钟与随机数、
可被假时钟测穿、状态可持久化的策略对象。

四层里的位置：

```
changqing   我记得什么           （记忆）
huatou      我什么时候说、说什么   （决策）  ← 本仓库
echoturn    我怎么说出去          （表达）
touchstone  我怎么知道它变好了     （验收）
```

---

## 1. 它解决什么问题

一个「陪着你」的 Agent 与一个「应答机」的区别，几乎全在这四件事上，而它们都**不是**生成质量：

1. **该她先开口时她开口。** 两个人四秒没说话，通话里已经很久了；文字里十秒才算久 ——
   两个数字不一样，因为两种场合的沉默含义不一样。
2. **不该开口时她闭嘴。** 手里什么素材都没有还要「起个头」，只能靠编，
   而用户读到的就是「她说的话跟我完全无关」。
3. **试过就不再纠缠。** 连续两次没得到回应就停下来等用户 ——「她试了两次就不再打扰你」
   本身就是真人感的一部分，不只是省钱。
4. **说出来的话能听。** 安静十秒后开口的第一句是「你好」，把「她想起你了」
   变成了「她只会打招呼」；同一句「今天画了五版」再发一遍，读起来是她只剩这一句话。

这四件事在源系统里全部存在、全部有真机证据、全部是可机械判定的 —— 但它们散落在
`turn.py` 的六个函数、`config.py` 的六个数、`llm/text.py` 的一堆正则、
和前端 JavaScript 的一个定时器里，**没有一个地方能回答「她为什么没开口」**。

huatou 就是那个地方。

## 2. 边界

### 管

| 判定 | 回答的问题 |
|---|---|
| `may_open()` | 现在允许她主动开口吗 |
| `should_hand_back()` | 这一轮答完，要把话头递回去吗 |
| `must_wait()` | 她问过之后，是否必须等用户真实开口 |
| `line_rejected()` | 这一句能不能出口（空转 / 重复 / 禁用句） |

### 不管

| 不管 | 归谁 |
|---|---|
| 话头说什么内容、从哪条事实起头 | changqing 的话题层 + LLM |
| 话头怎么落到气泡里（并进原条 / 单独一条、怎么拆） | 表达层（Echoturn 的 text 层） |
| 怎么合成、怎么播放、怎么打断 | Echoturn |
| 用户说话了要不要回 | 流水线 —— 用户说了就必须回，那不是策略，是契约 |

### 依赖方向

**huatou 不 import 任何东西。** 核心是纯标准库，不认识记忆、不认识模型、不认识传输。

它需要外界给两样东西，都用协议注入：

- `MaterialProbe`：`has_material() -> bool`。**它自己不查库**，因为「有没有料」是记忆层的知识。
  源系统在这里踩过一次坑值得抄下来：内容闸曾经读的是上一轮的注入工作面
  （`sess["_mem"]`），而闸门跑在 `prepare_turn` **之前**，那时它还是旧的、而且不落盘 ——
  症状是「她永远不开口」，看起来像功能坏了。所以判据必须是**直查**，不能读缓存的工作面。
- `Clock` / `Rng`：默认可以取 `time.time` / `random.random`，但**必须可注入**。

## 3. 状态机

### 3.1 状态（宿主可持久化）

```
streak          连续主动开口了几次（用户一开口就清零）
last_open_ts    上一次主动开口的时刻
text_fired      文字端「这一回合已经主动挑过一次」
waiting_user    她问过一个带话头的问题，正在等用户真实回话
her_ask_streak  她连着几轮都在问他（「连问闸」用，见 §3.5）
```

`her_ask_streak` 有一条**向前兼容**要求值得抄：老状态里只有布尔量 `last_her_ask`，
读回来时要当成「连问了 1 轮」—— 回落之后她照样能被允许再问一轮，
而不是因为一个读不出来的字段**永远卡住**。状态迁移的失败姿态必须是放宽，不是锁死。

四条字段全部要能 `to_dict()` / `from_dict()`。源系统的理由是产品需求：
用户刷新页面后，**已经用掉的机会与「问后等待」都从 `/api/state` 读回来**，
不因刷新重新布防 —— 否则刷一下就能骗她再问一次。

### 3.2 事件

```
user_spoke     用户发来一条非空消息       → 全部清零，重新布防
opened         她主动开口了一次（放行且真的发了） → streak += 1, last_open_ts = now
her_ask(asked) 她这一轮出稿里有没有在问他  → waiting_user = asked
```

三个 `note_*` 是**唯一**改写状态的入口。判定函数只读不写。

### 3.3 转移

```
                    user_spoke
   ┌────────────────────────────────────────┐
   │                                        │
   ▼                                        │
IDLE ──silence ≥ 阈值 且 四道闸放行──► OPENED ──她的出稿里有问句──► WAITING
   ▲                                                              │
   └──────────────────── user_spoke ──────────────────────────────┘
```

三个状态之外还有一个终局：`streak ≥ max_streak` 时**不再布防**，
直到 `user_spoke` —— 这就是「她试过两次就不再打扰你」。

### 3.4 `may_open()`：四道判据，**按从便宜到贵排**

顺序本身是设计，不是实现细节：最贵的（要读库的内容闸）放最后。

```
1. max_streak ≤ 0        → 关掉这个功能（0 是开关，不是阈值）
2. waiting_user          → 她问过，没等到回话就不再开口
3. text_fired（仅文字端） → 文字端一个真实回合只主动挑一次
4. streak ≥ max_streak   → 试过了，等用户开口（终局语义）
5. material.has_material() → 手里一点素材都没有，这次不开口（这道要读库，最贵）
6. now − last_open_ts ≥ min_gap_sec
```

任何一条不满足都要返回**理由**，不许返回裸布尔。理由串是运维面板上那一行
「她为什么没开口」，也是评测里接话率的分母注解。

### 3.5 `should_hand_back()`：递话头

这是一次**抽签**，不是提示词里的一句「大约一半的时候反问」。
源系统明确写过理由：**模型对概率式指令的服从度不稳**（要么全问、要么全不问），
而抽签是确定性的 —— 注入 `rng` 之后，两个方向都能被测试钉死。

三道闸，按从便宜到贵，**抽签放最后** —— 没抽中就不消费随机数，
否则「这一轮被闸挡下」与「这一轮抽签没中」在可复现性上会混成一个信号：

```
① 用户这一句够长（≥ min_units）      → 太短就没什么可接的
② her_ask_streak < max_ask_streak   → 连着两轮都问过，这一轮必停
③ 抽签（rng < ratio）                → 允许，但仍由模型决定措辞
```

**连问闸的粒度是「一段」不是「一轮」。** 一个 1.0 的比例（文字端能问就问）
必须有东西压着，否则她会变成一台追问机；压着它的四样东西是
**长度闸 / 连问闸 / 纯寒暄逃逸口 / 模型服从度**（判定式评测实测「抽中之后递到」
63%–74%）。连问闸卡掉的是「一段对话里她连着问三轮」，粒度比长度闸粗一档。

抽中只是**允许**她递话头：他这句本身没什么可接的，她仍然可以不问 ——
这就是「纯寒暄逃逸口」。**它目前只在 prompt 里**（三层防线审计里「机器」那一格是空的），
所以它是一条「模型高兴才算」的规则。huatou 不假装能把它机械化：
逃逸口要么由宿主注入一条判据，要么照实标成 prompt-only，**不许写一条假的地板**。

两档比例与两档长度，因为**机会多少不一样**，不是因为她该更黏人：

| | 比例 | 长度阈值 |
|---|---|---|
| 文字 | `1.0`（能问就问） | 4 字 |
| 通话 | `0.95` | 2 字 |

通话档比例更高，是因为他每句都短、还常被 VAD 切碎，同一份比例在文字里正常、
在电话里听着就是冷淡。通话档长度阈值更松，同理：电话里大半句是「嗯。」「我喜欢。」

**长度判据只能有一份。** 源系统把它单独拎成函数，正是因为它有两个消费方 ——
放行的抽签，和评测报接话率时的分母。他只有「嗯」「还行」「就那样」这种回声的轮次，
机制本来就不该递话头；把这些轮次算进分母，只会把实到率报低一档
（真机实测：全部轮次 65%，只算够长的轮次 71%）。评测里再写一遍判据，两边就会各漂各的。

### 3.6 阈值表（`Dials` 的全部条目）

调用时现读，不许在导入期快照。左列是建议的字段名，右列是源系统的实测默认值。

| 字段 | 默认 | 含义 | 为什么是这个数 |
|---|---|---|---|
| `open_text_sec` | 10 | 文字端安静多久算可以开口 | 文字端太主动会显得黏人 |
| `open_call_sec` | 4 | 通话端安静多久算可以开口 | 通话里 4 秒沉默已经很长 |
| `max_streak` | 2 | 连续主动开口上限（0 = 关掉功能） | 「试两次就不打扰你」本身是真人感 |
| `min_gap_sec` | 8 | 两次主动之间至少隔多久 | 与 `open_call_sec` 一起降（20 → 8）：不一起降的话她会一直「想开口但被挡」 |
| `hand_back_ratio_text` | 1.0 | 文字端答完递话头的概率 | 能问就问；由长度闸与连问闸压着 |
| `hand_back_ratio_call` | 0.95 | 通话端同上 | 更高，因为**机会更少**（他每句都短、常被 VAD 切碎） |
| `hand_back_min_units_text` | 4 字 | 文字端长度闸 | 4 字以下没什么可接的 |
| `hand_back_min_units_call` | 2 字 | 通话端长度闸 | 通话里大半句是「嗯。」「我喜欢。」，4 字会挡掉大半轮 |
| `max_ask_streak` | 2 | 连着几轮都问了就必停一轮 | 「答完把话头递回去」要成为默认行为，就必须有东西压着它 |
| `dedup_window` | 5 | 逐字重复比对她最近几条 | 五条足够覆盖「她只剩这一句话」的观感 |

**门限是「起点」还是「实测值」，必须逐条写清楚。** 源系统在这件事上立过规矩：
能量 VAD 的门限在它定义的地方就写明「只是起点、不是实测值」。
这张表里 `hand_back_ratio_*` 与 `max_ask_streak` 有真机依据（判定式评测的接话率），
`open_*_sec` 是产品口径（用户直接给的期望），`dedup_window` 是拍的 ——
**照实标出来，别让下一个实现者以为它们一样硬**。

## 4. 判据详解

这一节是设计稿里最需要保真的部分。每一条都带源系统的真机证据和日期 ——
**证据是判据的一部分**，因为它解释了「为什么放宽到这里就停」。

### 4.1 「她有没有在问他」——`asks_the_user`

**判据不是「带问号」。** 源系统真机实测：她那串自问自答的两句问号都没有；
而紧接着那条定时主动就把话续上了，用户读到的就是「她替我答了」。
所以这一档要认六七种形状，按优先级：

| # | 形状 | 判据 | 真机来源 |
|---|---|---|---|
| 1 | 问号收口 | 结尾是 `?` `？` | 常规 |
| 2 | 疑问词 | `什么 / 怎么 / 咋 / 哪[儿里个天] / 几点 / 多少 / 谁 / 几[个天] / 是不是 / 有没有 / 要不要 / 好不[好嘛] / 行不行 / 知不知道 / 记不记得 / 想不想 / （逗号后的）还是`，**并且**排除否定前缀（没什么 / 不怎么 / 哪有 / 别无） | 真机「最近怎么了呀」 |
| 3 | 句中「吗」 | **不挑位置** | 真机「…你呢，今天不是坐了很久地铁吗，现在到哪了」——收口是「到哪了」，老判据认不出 |
| 4 | A 不 A | 收口在一个裸「没」上，且前面不是「还不也都没」 | 真机「你到宿舍了没」三句 |
| 5 | 语气词收口（硬档） | `吗` `么` | 常规 |
| 6 | 语气词收口（软档） | `吧呢呀啊呗嘛`，**且句中出现第二人称**（你 / 您 / 咱） | 真机「你不是说这几天要调养嘛」 |

三处**刻意不放宽**，每一条都有量过的理由，别当成遗漏：

- **「哦」不收**：会与陈述句大量混淆；源系统没有语料证据支持。
- **句中的「么」不照搬「吗」的放宽**：它同样长在「这么 / 那么 / 多么」里。
  量过语料：517 条里只加「吗」多认 2 条，两条都在问他；「么」一条都没多认。
- **「干嘛 / 啥」刻意不收**：语料里她问句后面紧跟的三条里，两条是她**自己的**那一天
  （画廊是她的实习地），收进来会把她自己的话吃掉。
- **「几遍 / 几次」没有跟着放宽**：每次只按量到的那一种形状加，
  不然这一档会变成「带个数字就算问」。

**已知的误认照实记**：带「谁」的陈述（如「我实习的画廊也是，谁跟谁好一眼看出来」）
也会算成问句。源系统算过这笔账并**选择认它**：这条判据的用途全都指向
「问过就停下来等他」，所以**漏她（继续追问）比误认她（停下来等）更贵**——
误认的代价是「她少问一句」，漏掉的代价是「她替他把答案说了」。
这是一条**不对称**的账，必须写进文档，否则下一个人会按对称的直觉往回改。

**这条判据只有一份。** 表达层在做「剥掉自问自答」时也读它 ——
但 huatou 是它的**唯一实现**，表达层 import 它。

### 4.2 出稿闸：空转与逐字重复 ——`line_rejected()`

只判**主动开口的第一句**。后面几条是她展开的内容，拿黑名单去卡会把
「你还好吗」这种真的关心话误伤。

```
归一化：re.sub(r"[\W_]+", "", text).lower()        # 「你好」「你好！」「你好～」是同一句
① 归一化后为空（纯标点 / 表情）      → 拒绝，「不是话」
② 命中空转黑名单（24 条纯问候）      → 拒绝
③ 与她最近 5 条 assistant 消息里说过的任意一句逐字相同 → 拒绝
```

三条设计要点：

- **黑名单要归一化后再比。** 不归一化的话，模型在尾巴上加个标点就绕过去了。
  24 条是：你好 / 您好 / 你好呀 / 你好啊 / 你好哇 / 在吗 / 你在吗 / 在不在 / 在么 / 在嘛 /
  最近怎么样 / 最近好吗 / 你最近好吗 / 你还好吗 / 还好吗 / 最近还好吗 / 早上好 / 早安 /
  哈喽 / hi / hello / 在干嘛 / 你在干嘛 / 干嘛呢。
  「你好呀，今天画室特别安静……」不算 —— 那是真的在说话，判据是**整句相等**。
- **重复那条按「句」比，不按「条」比。** 历史里一条消息常常是好几句，
  而这里收到的是切句之后的一句；整条 vs 一句时两条判据永远对不上。
  真机上出过这一次：她安静十秒后主动开口，又把上一条消息里的半句一字不差说了一遍。
  **两边必须过同一个切句器**（由宿主注入 `SentenceSplitter`，见 §5），才算同一个判据。
- **黑名单是「确定性兜底」，不是唯一防线。** 真正的把关在内容闸（§3.4 第 5 条）；
  这里只挡最能一眼看出没料的那一种。

### 4.3 禁用句（机械那一层目前是空的）

「你怎么不理我」「你怎么不回答我的问题」「你都不睬我」这三句，
在源系统里**只写在 prompt 里**。按它自己的三层防线审计
（prompt 说一遍 / 机器兜一道 / 度量看得见），这三条的「机器」一格是空的 ——
也就是「模型高兴才算」。

huatou 把它补成第二层：一个可扩展的**禁用句表**（精确匹配 + 归一化匹配两档）。
这不是新功能，是把一条已经承诺过、但没有确定性保障的规则补齐。

```python
@dataclass(frozen=True)
class Verdict:
    allowed: bool
    reason: str            # "waiting_user" / "no_material" / "min_gap" / ...
    detail: str = ""       # 给人看的一句话
```

**判定一律返回 `Verdict`，不返回裸布尔。** 理由是运维面的要求：
面板上要能写出「她为什么没开口」，而不是让用户猜。
源系统里这一格是空的 —— 表现就是「她记性不太好 / 她怎么不理我」，谁都查不出来。

## 6. 硬约束（抽象时最容易丢的十二条）

每条都要以「代码 + 一条能失败的测试 + docs 里的理由」三件套落地。

1. **核心零第三方依赖**，纯标准库。`pip install .` 之后 `import huatou`
   不许把任何第三方模块带进 `sys.modules`（CI 里断言这一条）。
2. **判定必须是纯函数**：`(state, now, params) → Verdict`。不许在判定里调
   `time.time()` 或 `random.random()` —— 时钟与随机数由构造器注入。
   这样「安静 9.9 秒不放行、10.1 秒放行」可以用假时钟精确钉死。
3. **判定与推进分离**。判定只读，`note_*` 才写。混在一起的话，
   「这一次放不放行」和「放行之后状态怎么变」会有两处真源。
4. **`may_open` 的四道判据按从便宜到贵排，且顺序本身有测试钉住。**
   内容闸读库，必须最后跑 —— 否则每个不放行的轮次都要白开一次库。
5. **阈值只有一张表**（`Dials`），**调用时现读**，不许在导入期快照成模块级常量。
   源系统在这上面踩过两次，症状一模一样：猴补配置改不到它，而且**不报错**。
6. **状态可序列化**（`to_dict` / `from_dict`），宿主能持久化、能跨刷新继承。
   不能序列化的状态等于「刷新就重新布防」，而那是一条能被用户利用的漏洞。
7. **任何内部异常都退化成「这次不开口」，但不能静默。**
   沉默是唯一允许的失败姿态（宁可少说一句，不可胡说一句），
   但必须留下 reason —— 「她为什么没开口」永远要答得出来。
8. **判据的检测模式自备一份**，不许复用表达层的清洗实现。
   源系统的原话：**评测与实现同源就等于没有评测** ——
   谁把清洗层里那几条正则改空，指标会跟着一起变成 0，而一切看起来正常。
9. **逐字重复按句比**，两边必须过**同一个**切句器（由宿主注入）。
   注入而不是内置，是为了让「两边同源」这件事在类型上就成立。
10. **不对称的判据要把账写下来。** 哪些放宽、放宽多少、误认与漏掉哪边更贵 ——
    写进 `docs/rules.md`，每条带真机证据与日期。不带证据的放宽等于拍脑袋。
11. **反向用例必须能真的红。** 每条判据都有一条「证明它能拒绝」的用例，
    并且这条用例要能因为实现改坏而失败（不是恒真的对照物）。
12. **不许内部读环境变量。** 配置由宿主显式传入 `Dials`，或由宿主自己从环境变量组装。
    一个库背着调用方去读环境，症状是「我以为它没配，它却在按别的规则走」。

## 9. 明确不许做的事

- 不许把产品的判据、黑名单、阈值之外的任何东西带进来（尤其是角色名、产品名、领域词）。
- 不许把「有没有料」硬编码成某种存储查询 —— 内容闸必须是注入的协议。
- 不许为了让第一版好写而放宽任何一条判据，或删掉任何一条反向用例。
- 不许用 `sleep` / 真时钟写测试：**所有时间相关用例必须用假时钟**。
- 不许把阈值写成导入期常量（见硬约束 5）。
- 不许在文档里复述源产品的数字，除非它是这条判据的**证据**，且带日期。
- 不许「因为难测」而把判定和状态推进合并。
